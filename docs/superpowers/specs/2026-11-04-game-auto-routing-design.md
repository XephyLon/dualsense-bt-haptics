# Game auto-routing over Bluetooth — design (phase 2)

Date: 2026-11-04
Status: approved (approach 1)

## Goal

Games with native DualSense support (haptics via the controller's 4-channel
audio device, adaptive triggers via HID output reports) get those features on
this machine while the DualSense Edge is connected over Bluetooth, under
Proton, with no per-game hacks.

## Why phase 1 alone is not enough

Phase 1 gives a PipeWire sink that any audio can be routed to. Native-haptics
games do not look for a sink by our name. From Proton's Wine source
(`dlls/winebus.sys/bus_udev.c`, `dlls/winepulse.drv/pulse.c`, branch
`experimental_10.0`):

- The HID device gets a `ContainerId` only when its bus is USB:
  `GUID{ MAKELONG(vid,pid), BUSNUM, DEVNUM, USEC_INITIALIZED }` of the USB
  parent. A Bluetooth HID device gets none.
- The audio endpoint gets its `ContainerId` from the PulseAudio/PipeWire
  property `sysfs.path`, resolved through udev to the same USB parent and the
  same formula.
- Games find the haptics endpoint either by friendly name "Wireless
  Controller" (FFXIV, FF7R) or by comparing `ContainerId`s (Deathloop,
  Ghostwire, Cyberpunk 2077, Assassin's Creed Shadows, libScePad titles such
  as Returnal and Death Stranding).

A virtual PipeWire sink can satisfy the name rule only. The container rule
needs a device the kernel itself sees as USB.

## Decision

Adopt **ds5bridge** (https://github.com/snooptheone/ds5bridge, GPL-3.0-or-later,
v0.1.0, 2026-10): a root daemon that, when a Bluetooth DualSense connects,
attaches a virtual USB DualSense to the kernel's `vhci_hcd` over an in-process
USB/IP socketpair. The kernel binds `hid-playstation` and `snd-usb-audio` to
it, so Proton's unchanged USB logic links HID and audio. The daemon bridges:
input BT `0x31` → USB `0x01`; game output USB `0x02` → BT `0x31` (triggers,
LEDs); USB audio channels 3–4 → FIR low-pass → int8 3 kHz → BT `0x39`;
channels 1–2 → Opus → the same `0x39`. It hides the real pad's hidraw/evdev
nodes (root-only) so Steam and games see one controller. A WirePlumber rule
names the virtual pad's sink "Wireless Controller", 4-channel S16LE 48 kHz,
unmixed.

We do not reimplement this. Our contribution is validation on hardware the
upstream project has not covered (DualSense Edge 054C:0DF2, MediaTek MT7921
adapter, GE-Proton 10 / Proton Experimental 11 / Proton-CachyOS), fixes
upstream if needed, and integration with the phase-1 tools.

## Components and changes in this repo

1. `docs/research/2026-11-04-proton-dualsense-matching.md` — how Proton
   matches HID to audio (the facts above, with file/function references),
   what ds5bridge does, what we measured.
2. `tools/ds5-mirror.sh` — mirror a PipeWire node's monitor into the virtual
   pad's haptic channels (`Wireless Controller:playback_RL/RR`) with
   `pw-link`, for games without native haptics while ds5bridge is active.
   Phase 1's `ds5-haptics-sink` cannot run at the same time as ds5bridge
   (the real pad becomes root-only and two writers would collide), so this
   is the mirror path when ds5bridge is installed.
3. README: a "Games (ds5bridge)" section: install, Steam Input off per game,
   which Proton builds were verified, the mirror helper, how to switch back
   to phase 1 (stop/disable `ds5bridge.service`, or `sudo make uninstall`).

ds5bridge itself is installed system-wide from its own source tree
(`make && sudo make install`, or its Arch PKGBUILD); it is not vendored into
this repo. Any patch we need is kept under `contrib/ds5bridge/` as a `.patch`
and submitted upstream.

## Validation plan (hardware, manual)

1. `make test` of ds5bridge passes without hardware.
2. With the Edge on over Bluetooth and the service running: `journalctl -u
   ds5bridge` shows the pad detected, feature reports read, virtual pad
   attached, QoS result; `lsusb` shows a Sony 054c device on the vhci bus;
   `pactl list sinks short` shows the "Wireless Controller" 4-ch sink;
   `ls /dev/hidraw*` shows the real pad root-only and a new USB-bus
   DualSense; `python3 -m ds5bt info` finds nothing (expected: real pad is
   now root-only and the virtual one is USB).
3. Haptics through the virtual pad without a game: `pw-play --target
   "<Wireless Controller sink>"` of a 4-channel WAV with content only on
   channels 3–4 (generated by `tools/make_test_wav.py --4ch`).
4. Games, Steam Input disabled for each: Cyberpunk 2077 (ContainerId
   matching), FFXIV (name matching), Lies of P. Expected: haptics felt,
   adaptive triggers active. Try Proton Experimental first, then GE-Proton
   10-34 and Proton-CachyOS.
5. Reconnect: power the pad off and on mid-session; the virtual pad goes away
   after 3 s and comes back; the game's trigger effects are replayed.
6. Record everything in the README and the research doc.

## Error handling / rollback

- `sudo systemctl stop ds5bridge; sudo systemctl disable ds5bridge` restores
  the real pad (udev rule 72 only hides it while `vhci_hcd` is loaded;
  `sudo modprobe -r vhci_hcd` undoes that too).
- `sudo make uninstall` in the ds5bridge tree removes everything it installed.
- If the Edge misbehaves in ds5bridge (descriptor or report differences),
  capture `journalctl -u ds5bridge` and `btmon`, patch, keep the patch under
  `contrib/ds5bridge/`.

## Out of scope

Microphone bridging (upstream marks it unproven), speaker quality tuning,
multiple pads, non-Proton native Linux games (none known to use DualSense
haptics).
